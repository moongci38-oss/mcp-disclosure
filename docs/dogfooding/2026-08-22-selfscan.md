## 발견 ① [치명] 스캔이 아예 안 됐는데 "깨끗하다"고 보고했다

**첫 실행은 스캐너를 PATH 에 넣지 않고 돌렸다.** 바이너리를 못 찾아 스캔 성사 0건이었는데,
소견서는 기술축 5개에 대해 **"검사했지만 못 찾았다"**를 찍었다. `Unscanned items` 한 줄은
문서 **맨 아래**에 있었다.

쉽게 말하면 **없는 폴더를 뒤져놓고 "양말이 없네"라고 한 셈**이다. 이 제품이 존재하는 이유와
정확히 반대되는 출력이라, 다른 어떤 결함보다 심각하다.

- **원인**: `mapFindingsToClaims` 가 스캔 성사 여부를 몰랐다. 입력이 "finding 0건"이면
  "검사했는데 없음"과 "검사 자체를 못 함"이 **구분되지 않는다.**
- **조치**:
  1. `ScanOutcome { attempted, scanned }` 신설 — `mapFindingsToClaims` 의 **필수 인자**로 뒀다.
     기본값을 두면 호출부가 깜빡했을 때 조용히 "스캔했음"으로 처리돼 같은 사고가 재발한다.
  2. 성사 0건이면 기술축을 `scanner_cannot_detect` + 사유로 낸다.
  3. 스캔 실패 배너를 **문서 맨 위**로 올렸다 — 정직성을 읽는 사람의 주의력에 맡기지 않는다.
- **회귀 테스트**: `map.negative-fixture.test.ts` 4건 + `cli.exit-codes.test.ts` 1건(실행 경로 전체).
- **재현(수정 전)**: PATH 에 `mcp-scanner` 없이 `node dist/src/cli.js scan --path <dir>` →
  2절에 기술축 5개가 "no findings" 로 나온다.

## 발견 ② [높음] 재현 메타 자리표시자가 게이트를 무사통과했다

`ruleset_hash: 'unset'`, `target_hash: 'unset'`, `version: 'unknown'` 이 그대로 소견서에 실렸다.
`assertMetaComplete` 는 **빈 문자열만** 검사해서 자리표시자를 통과시켰다 —
**"가드가 있다"와 "가드가 막는다"는 다른 주장**이라는 이 프로젝트의 반복 교훈이 또 나왔다.

- **조치**: 자리표시자(`unset`/`unknown`/`n/a`/`tbd`/`-`)를 `RenderError` 로 막고,
  실측된 부재는 `unavailable` 로 구분해 통과시킨다. `target_hash` 는 실제로 계산한다
  (읽은 설정 파일 내용의 sha256 앞 16자) — 같은 설정을 다시 스캔했는지 확인할 유일한 수단이라
  이 값만은 실값이어야 한다.
- **남는 부재(정직 표기)**: `version`·`ruleset_hash` 는 **원래 못 얻는다** —
  이 스캐너에 `--version` 플래그가 없다(Session 1 실측, argparse exit 2). 소견서 상단 경고에
  그 사실과 영향("정확한 스캐너 빌드를 못 박을 수 없다")을 함께 적는다.

## 발견 ④ [낮음] `supportedScannerRange: "0.x"` 가 실제와 어긋난다 — **2026-08-22 조치 완료**

`package.json` 의 지원 범위가 `0.x` 인데 실제 대상은 4.8.3 이다. 지금은 `--version` 자체가 없어
버전 검사가 **항상 건너뛰어지므로** 증상이 드러나지 않는다 — 즉 이 값은 **현재 아무 일도 하지 않는다.**
스캐너가 나중에 `--version` 을 갖게 되면 그날부터 매 실행이 "범위 밖" 경고를 뱉는다.

- **미조치 사유**: 고치려면 "무엇을 지원 범위로 선언할 것인가"를 정해야 하는데, 실측한 버전이
  4.8.3 **하나뿐**이라 범위를 정할 근거가 없다. 근거 없이 `4.x` 로 넓히면 그것도 거짓말이다.
- **조치(같은 날 Spec 감사)**: 범위를 **추정하는 대신 개념을 바꿨다** — `supportedScannerRange`
  (지원 범위, 근거 없음) → `testedScannerVersions: ["4.8.3"]`(검증한 버전, 실측 기반).
  `4.x` 로 넓히지 않은 이유는 여전히 같다: **실측한 버전이 하나뿐이라 근거가 없다.**
  구 구현은 우리가 전부 검증한 유일한 버전을 "범위 밖"으로 판정하고 있었다.
  fixture 디렉터리도 `mcp-scanner-0.1.0/` → `mcp-scanner-4.8.3/` 로 개명했다.

# 2차 도그푸딩 — YARA 라이브 발화 (같은 날, Spec 감사 후속)

1차 실행의 남은 구멍은 **YARA 가 한 번도 발화하지 않았다**는 것이었다. 대상이 무해했기 때문이고,
그 탓에 `accepts_taxonomy`(taxonomy 매칭) 경로가 실행 경로에서 **한 번도 검증되지 않은 채** 있었다.

## 방법

Cisco 예제 악성 서버는 python `fastmcp` 를 요구하는데 설치돼 있지 않았다(`uv pip install` 시도했으나
해당 모듈 부재). 그래서 **의존성 0인 Node stdio MCP 서버**를 직접 만들었다 —
`fixtures/servers/malicious-stdio-server.js`. JSON-RPC 를 직접 말하며, 도구 **설명 문자열**에만
탐지 대상 패턴을 담는다(어떤 위험한 동작도 하지 않는다).

```bash
export PATH="/tmp/agenttrust-scanner-venv/.venv/bin:$PATH"
node dist/src/cli.js scan --path <dir>   # dir/.mcp.json → 위 fixture 서버
```

결과: findings **40** · 미분류 **0** · YARA 3종 발화(`PROMPT INJECTION`, `CREDENTIAL HARVESTING`+
`DATA EXFILTRATION`, `CODE EXECUTION`).

## 발견 ⑤ [높음] taxonomy 를 옆 finding 에서 빌려 쓰고 있었다

`sync_profile` 도구의 yara 롤업이 **threat_names 2개에 taxonomy 1개**를 냈다:

```
threat_names: ["CREDENTIAL HARVESTING", "DATA EXFILTRATION"]
mcp_taxonomies: [{ aisubtech: "AISubtech-8.2.3" }]
```

파서는 "taxonomy 가 정확히 1개면 채운다"였으므로 그 하나를 **팬아웃된 두 finding 양쪽에 복사**했다.
`AISubtech-8.2.3` 은 `secret_exposure` 소유이고 taxonomy 는 signal_map 을 이기므로(§5.3),
`DATA EXFILTRATION` 이 `malicious_pattern` 대신 **`secret_exposure` 로 분류**됐다.

소견서가 **"데이터 반출 패턴"을 "시크릿이 노출됐다"로 잘못 말한 것**이다. 등급이 아니라 종류가
틀린 오분류라, 읽는 쪽이 엉뚱한 곳을 조사하게 된다.

- **조치**: `resolveTaxonomy` 의 조건을 둘로 늘렸다 — taxonomy 1개 **AND threat_name 1개 이하**.
  짝을 모를 때 하나를 빌려 쓰는 것은 관측이 아니라 추정이다.
- **수정 후**: `DATA EXFILTRATION` → `malicious_pattern` ✅ · `CREDENTIAL HARVESTING` → `secret_exposure` ✅
- **회귀 고정**: 단위 2건 + 라이브 캡처 fixture 기반 통합 2건
  (`fixtures/mcp-scanner-4.8.3/raw-envelope-malicious-live.json` — 스캐너 없이도 이 분류가 고정된다).
- **재현(수정 전)**: 위 봉투를 `parseScannerRawEnvelope` → `normalize` 에 통과시키면
  `DATA EXFILTRATION` 의 `axis` 가 `secret_exposure` 로 나온다.

## 발견 ⑥ [중간] 테스트가 "이 머신에 스캐너가 없다"는 우연에 기대고 있었다

`cli.exit-codes.test.ts` 의 "스캔 0건" 회귀 테스트는 `mcp-scanner` 가 PATH 에 **없다는 전제**로
쓰여 있었다. 스캐너를 설치한 머신에서 돌리자 전제가 깨져 FAIL 했다 — 테스트가 환경에 따라
결과를 바꾸면 그건 회귀 테스트가 아니다.

- **조치**: PATH 를 직접 통제한다(python 셰임만 있는 임시 디렉터리). `node` 도 PATH 로 찾으므로
  `process.execPath` 절대경로로 띄운다.
- **확인**: 스캐너가 **있는 상태**와 **없는 상태** 양쪽에서 164/164 GREEN.
